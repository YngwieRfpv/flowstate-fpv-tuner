Ablauf

Wie eine Version ihren Platz findet

Von der losen Datei im Drive bis zur aufrufbaren URL sind es fünf Schritte. Jeder Schritt hinterlässt eine Spur, die man später prüfen kann.

Quelle

Version liegt im Drive-Ordner GitHub Versionen — mit eigenem Unterordner je Ausgabe.

Einordnen

Projekt, Kanal, Datum, Größe und Prüfsumme landen in versions.json.

Einspielen

Die Einzeldatei wird zu tuner/index.html bzw. guide/index.html.

Prüfen

Ausliefern

Versionen

Der vollständige Index

Eine Karte pro Ausgabe — mit Kanal, Prüfsumme und ehrlichem Reifegrad. Die Liste wird aus assets/data/versions.json erzeugt; neue Versionen brauchen nur einen Eintrag, keine HTML-Änderung.

Struktur

Ein Repository, zwei Anwendungen

Kein Build, keine Abhängigkeiten, keine Serverlogik. Alles, was GitHub Pages braucht, ist die richtige Ordnerstruktur und eine .nojekyll-Datei. 

flowstate-fpv-tuner/
├── index.html              # dieser Hub
├── README.md               # Einstieg & Regeln
├── .nojekyll               # Jekyll aus, Assets unangetastet
├── .gitignore
├── .github/workflows/
│   ├── pages.yml           # Deploy nach Pages
│   └── validate.yml        # Index & Hashes prüfen
├── guide/
│   └── index.html          # FPV Guide DE
├── tuner/
│   └── index.html          # FlowState Tuner
├── assets/
│   ├── css/style.css     # Design-System des Hubs
│   ├── js/hub.js          # Rendering & Filter
│   ├── data/versions.json # ← Quelle der Wahrheit
│   └── images/*.svg
├── docs/
│   ├── GITHUB_PAGES_SETUP.md
│   ├── RELEASE_PROCESS.md
│   └── releases/           # Notes je Version
└── scripts/
    ├── install-versions.sh # Dateien einspielen

    └── validate.mjs        # Prüfung
index.html

Der Hub bleibt schlank: Er beschreibt und verlinkt, er enthält die Anwendungen nicht.

versions.json

Einzige Quelle für Versionen, Kanäle, Hashes und Herkunft. Wer eine Version ergänzt, ergänzt hier einen Eintrag.

tuner/ · guide/

Feste URLs pro Projekt. Die Seiten bleiben unabhängig austauschbar — eine neue Version ersetzt genau eine Datei.

.nojekyll

Verhindert, dass GitHub Pages Dateien mit Unterstrich oder bestimmten Namen wegfiltert.

docs/

Release-Notes und Prozesswissen versioniert neben dem Code — nicht in einem Chatverlauf.

Deployment

In drei Schritten online

Der Hub ist statisch. Nach dem Einspielen der beiden Anwendungsdateien genügt ein Push, damit GitHub Pages die Seite ausliefert.

1

Versionen einspielen

Die beiden Einzeldateien aus dem Drive-Ordner an ihren Platz kopieren.

$ ./scripts/install-versions.sh \
    --tuner  ~/Downloads/FlowState-Tuner-v4.8-alpha.1.html \
    --guide  ~/Downloads/index.html

Das Skript kopiert, berechnet SHA-256 und Größe und trägt beides in versions.json ein.

2

Prüfen

Der Validator kontrolliert Index, Dateien, Hashes und interne Links.

$ node scripts/validate.mjs

Dieselbe Prüfung läuft bei jedem Push in GitHub Actions.

3

Pushen

Committen und pushen — der Workflow pages.yml deployt anschließend automatisch.

$ git add -A && git commit -m "release: tuner v4.8-alpha.1" \
    && git push origin main

Pages-URL: https://yngwierfpv.github.io/flowstate-fpv-tuner/

Alternative ohne Actions

Settings → Pages → Deploy from a branch → main / (root) funktioniert ebenfalls, weil .nojekyll vorhanden ist. Die Action-Variante ist nur reproduzierbarer, weil sie vorher validiert.

Reifegrad — ehrlich benannt

Beide Ausgaben sind vorab: der Tuner Early Alpha, der Guide GitHub-Beta. Bestandene Quellprüfungen sind kein Nachweis für Browser-, Web-Serial-, FC- oder Flugverhalten. Der Tuner schreibt nur nach explizitem Backup-Gate; Props ab für Bench-Arbeit, und bei heißen Motoren, Desyncs oder unklarer Mechanik sofort aufhören. Für dieses Repository ist noch keine Lizenz gewählt.
